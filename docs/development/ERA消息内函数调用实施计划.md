## 1. 目标与当前基础

角色卡作者通过 SillyTavern 注册 JavaScript 工具函数，自行定义参数和函数逻辑，支持条件、循环、字符串、多变量操作和异步调用。同名注册覆盖及工具执行复用酒馆能力；ERA 解析消息内调用，提供绑定执行位置的 API 上下文。酒馆原生工具调用维持原有使用方式。

**ERA 在内存中逐块、按顺序执行；commit 在操作实际生效后返回；聊天记录和 Sidecar 在批次提交边界保存。** 主工作流组织处理范围和生命周期，消息操作与 API 操作共用唯一的块执行流程，不复制第二套 CRUD、表达式、scope 或日志逻辑。

| 部分 | 当前实现基础 | 本计划目标 |
| --- | --- | --- |
| 正式同步 | 已有逐块执行、累计日志及逐块持久化路径 | 保留逐块计算，工作状态在内存推进，确定范围的处理结束后批量保存 |
| 公共 API | commit 等待 Service FIFO 任务结算；get 读取已发布的 Sidecar 缓存 | commit 等待内存实际应用，get 读取对应上下文的工作状态；持久化独立管理 |
| 消息内调用 | 保留解析及 done 判断；无 done 调用目前返回 ERA_FCALL_NOT_IMPLEMENTED | 实现作者函数执行、调用位置上下文及共用块执行调度 |
| 操作记录 | 普通 API 记录构造、scope 和旧格式读取可复用 | 函数使用同一普通记录格式，先累计消息变更，按批次保存 |
| 数值与历史 | statFunc、$expr、起点快照、随机序列、回退和压缩能力 | 保留既有变量语义，只调整状态发布、调度及保存责任 |
| 状态栏 | 楼层/Swipe 绑定、ready 等待、目标消息末尾写入 | 保留位置和就绪规则，读取工作状态时不串楼层 |
| Agent | 已有阶段交接与正文隔离规则 | 补齐规划草稿及规划、正文、结算中的顺序操作和调用 |

第一轮审核中的重复整楼计算、全局函数绑定等条目属于历史问题记录，不作为这些能力仍存在于当前代码中的断言。实施时以实际 source 和已登记 Architecture 为准。

## 2. 已确定的执行语义与生命周期

### 2.1 工作状态与逐块处理

1. 对新消息更新、历史重算或其他能够确定处理范围的同步，准备一份与当前聊天一致的内存工作状态。已有有效且尚未保存的工作状态必须被纳入后续处理，不能被旧 Sidecar 覆盖。
2. 工作状态包含变量、函数库、累计回退日志、scope 记录、执行位置及待保存的消息变更；Sidecar 保存其已持久化版本。内存中的当前状态与已保存状态是不同事实，不是两套独立变量引擎。
3. 沿用历史分歧定位与回退逻辑，确定消息范围和起点，再按原文顺序处理每一个 ERA 操作块。每块实际应用后更新工作状态，不强制保存聊天或 Sidecar。
4. 每条消息分别保留起点变量和函数快照，累计状态作为后续块的输入；@a、@f()、$expr、随机抽取序列及保护规则保持原有含义。
5. 消息最终状态来自逐块累计，不能再用另一份预先整楼计算结果覆盖。纯历史计算复用操作语义，但不产生写回或工具副作用。
6. 前面成功的块不因后面失败而自动回滚。发生错误时保留可解释的成功前缀及其日志和消息记录，按错误处理边界保存或恢复；不能宣布未执行部分已经完成。
7. 可以让出执行时间或分批调度，但调度让出不等于落盘。普通消息不引入固定64块等处理上限。

异步任务始终绑定聊天、消息版本和执行位置。编辑、删除、切 Swipe、切聊天后，按实际聊天重建受影响状态，旧计算不得覆盖新内容。

### 2.2 主工作流、函数调用与统一块执行

主工作流负责定位、回退、选取下一块、等待函数以及安排最终保存；消息中的普通块和 API 产生的操作共用一个块执行流程。

到达无 done 的调用时，主工作流等待作者函数结束，但不占有函数 API 所需的块执行位置。函数 API 携带显式调用上下文进入同一执行流程，应用到当前位置的工作状态后返回；函数结束后主流程继续后面的块。不能把这些 API 请求排在等待它们的完整同步任务之后。

```text
准备本批工作状态
消息块：HP = 100 → 内存 HP = 100
函数 A：读取 HP = 100
        await ERA.commit(HP = 70)
          → 共用块流程应用操作、日志、scope及待保存记录
          → 返回；未要求落盘
        再读取 HP = 70
函数结束 → 在待保存消息中标记 done
消息块：HP = HP × 2 → 内存 HP = 140
本批处理完成 → 保存消息变更 → 保存 Sidecar → 通知完成
```

函数对象只存在于 Host；Service/Host 边界传递可序列化事实。Host 不复制变量处理引擎，也不通过全局“当前正在运行某函数”推断 API 来源。上下文绑定解决调用位置和调度归属，不创建内外两种 commit 完成语义。

函数 API 已经实际应用的操作，本轮继续扫描消息时不得再次应用；生成记录用于保存及未来历史重放。本轮执行位置负责避免重复应用，不作为函数是否执行过的第二种判据。

### 2.3 commit、get 与顺序

**所有来源的 commit 都在操作实际应用到内存后返回，不等待持久化。** 返回前必须完成变量/函数状态、累计日志、scope 记录及待保存消息操作记录的更新；仅收集参数或请求入队不能报告成功。被 scope 正常跳过的调用保持真实的 skipped 结果。

| 接口或事实 | 含义 |
| --- | --- |
| await ERA.commit(...) 返回 | 操作已按顺序生效，或按 scope 明确跳过；不代表已落盘 |
| ERA.get() | 读取对应上下文的当前内存状态，不能因尚未落盘而退回旧 Sidecar |
| 同步/批次完成通知 | 对应处理及最终保存已完成 |
| 保存失败通知 | 工作状态未成功持久化，仍需保存或恢复；不能撤回已经返回的应用成功回执 |

同一有序执行域中，多次不 await 的 commit 按 ERA 接收顺序执行。防抖只合并保存，不合并或重排作者操作含义；前一请求失败应如实回执，不能据此把后面的请求算作已成功。

不 await 便立即同步 get，不保证尚在队列中的操作已经执行。作者需要顺序读回时 await commit；await 本身不会强制刷盘，也不会把本应合并的保存拆成多批。

外部 API 改动历史楼层时，仍按目标位置应用并安排必要的后续重算，不能把旧楼操作直接套到最新楼层状态上；相关工作状态应在回执承诺的读取范围内一致。

### 2.4 操作记录格式与插入位置

函数 API 产生的记录使用**与消息内状态栏 API 完全相同的格式**，包括既有事务/scope 表达。复用普通 era_tx 包装及 Variable/Function 操作构造，不建立新的函数专用 EraFCallTx 写入协议。

区别是目标位置：函数记录插入当前调用下方、原有后续操作之前；状态栏和外置脚本沿用原目标定位，记录在目标消息末尾。这里的插入首先发生在待保存消息内容中，不代表每次立即调用酒馆保存。

```text
前面的 ERA 操作
函数 A（处理后带 done）
A 第1次 API 的普通操作记录
A 第2次 API 的普通操作记录
原先后面的 ERA 操作
```

多次 API 按执行顺序追加到本次调用已生成记录之后，不反向插入。$expr 保存表达式，固定值保存固定值。调用位置只用于本次插入，不形成永久归属或压缩边界。锚点失效不能静默改为消息末尾写入。

### 2.5 临时进度与 done

| 信息 | 用途 | 保存与清除 |
| --- | --- | --- |
| 当前执行位置及临时进度 | 标识本轮已应用到哪里，避免本轮重复处理 | 平时随工作状态在内存推进；必要的中断保存须与日志一起保存，消息完成后清除 |
| 函数 done | 表示这一处函数已经尝试执行 | 先更新待保存消息，与对应 API 操作记录一起保存；完成消息和压缩均保留 |

**函数执行与否只看该调用有没有 done。** 不根据操作区、下方记录、名称、参数或另一份调用清单推断。

- 有 done：跳过函数本体，普通操作按当前位置正常处理。
- 无 done：正式处理到该处就尝试执行，即使下方已有旧记录。
- 不同调用独立判断；修改带 done 调用的名称或参数不会自动重跑。
- 用户移除 done 后再次尝试，旧操作不自动删除；编辑旧楼新增调用会顺序影响后续操作和楼层。
- 成功但没有变量操作的函数也标 done；失败规则见 §2.6。

当前解析已有自闭合语法，例如 `<EraFCall name="工具名" args='{}'/>`，以 `status="done"` 表达 done。准确公开语法在接口文档中统一，不能增加第二种执行历史判据。参数错误和嵌套引用识别属于解析规则。

### 2.6 失败、取消与职责边界

函数抛出未捕获异常或 Promise 拒绝时，退出调用、报告错误，保留此前成功的 API 操作，在待保存消息中标 done，然后处理后续块。未注册函数同样报错并标记；作者自行捕获异常继续运行时，ERA 正常等待。

API 应用失败返回真实失败；应用成功后发生的保存失败由 ERA 保存/恢复流程单独报告。不能把仅入队报告为成功，也不能把内存应用成功描述为持久化完成。保存失败时保留仍有效的待保存内容，尝试恢复，不清掉未保存操作或永久停服。

切聊天、编辑、删除、切 Swipe 或取消使上下文失效时，迟到结果不能修改新版本；基于已变化历史的工作状态须撤销或重算，而不是原样强行保存。规划取消遵守草稿边界。

ERA 的责任是自身变量、日志及 Sidecar 与实际聊天一致。强制关闭前仅在内存中的外部 API 请求无法恢复，作者脚本自行决定是否重发；ERA 不保证作者函数的网络、DOM或其他外部副作用只发生一次。scope 仅按实际作用域和已有记录工作：always 允许再次执行，未保存的去重依据可能丢失，不能以 scope 承诺崩溃后的普遍恰好一次执行。

### 2.7 压缩与历史重放

函数留下的普通 API 操作正常参与既有压缩，允许移动、合并，不要求留在原函数下方或保持归属关系。保留普通操作的有效语义、scope 和重放一致性。

done 调用参与正常消息处理但不执行本体，也不构成固定位置边界或整层跳过压缩的理由。压缩保留调用及 done；记录位置变化不会触发函数重跑。

沿用封存楼层的压缩范围，最新 AI 消息不参与封存压缩。未完成楼层先正确处理；清理临时进度及压缩结果归入本批消息变更，不因这些步骤单独逐块保存。

普通历史查询、状态栏快照、预览、纯试算和压缩校验不执行作者函数。正式历史同步按 done 判定调用，普通操作正常重算；“本轮避免重复应用”不表示历史重算永久跳过这些操作。

### 2.8 规划、正文与结算

```text
规划输出 → 顺序处理操作与调用，更新本轮草稿和阶段工作状态
→ 正文接收计划、函数结果及阶段状态
→ 正文完整接收并完成必要原生收尾
→ 顺序处理正文操作与调用
→ 结算接收更新后的状态，顺序处理补充操作与调用
→ 完成本轮消息变更及 Sidecar 保存
```

规划尚无正式 AI 楼层时，API 操作和 done 写入本轮规划草稿；成功后随最终消息保存，取消不能追加到上一条 AI 消息。后续阶段直接读取处理后的内存状态，不要求先保存 Sidecar。

规划、正文、结算中的 commit 都表示内存应用完成，不提供单独的“规划应用回执”与“正式楼层落盘回执”两种成功语义。独立结算开启时，正文变量指令和调用仍生效，结算提示词说明已经发生的变化，避免重复结算。

阶段内部放行可依据工作状态；面向作者的最终同步完成通知须等待相应保存完成。可执行输出与报告引用必须结构化区分。消息调用的执行不依赖 iframe 渲染或消息可见性。

### 2.8.1 阶段候选整体回退

规划按前置指令、原有calls、后置指令执行；结算直接输出六类 ERA 操作标签与 EraFCall，按原文顺序逐块执行，不使用 operations JSON 或转换包装，均读取当前位置状态。每个候选建立恢复点；出现可纠错错误时撤销整个候选的变量、函数库、日志、scope、随机偏移、草稿、操作记录、done及进度，再基于恢复后的状态生成完整候选。更早完成阶段保留，重试耗尽保留候选起点并报告失败。此规则是阶段纠错对成功前缀保留原则的明确例外。

普通作者函数自身抛错仍标done、保留成功操作并继续；若该候选后来被整体回退，其ERA效果也随之撤销。保存失败、取消和目标失效不作为模型纠错。先结清已接收API、使旧上下文失效再完成回退，迟到回调不得写入后续候选。commit表示当时内存已应用，不承诺候选后来不会被撤销；ERA不能撤销作者网络或DOM副作用。

替换阶段均在模型请求之前恢复保留部分的变量与函数库基线：重新规划保留本轮之前内容，重新正文保留本轮规划，原生 Regenerate 撤销被替换回复；Continue 保留现有内容并继续追加。

手动重新结算必须在模型请求之前恢复正文结束基线，撤销旧结算效果与记录；保留规划正文记录和done。新候选耗尽时显示未结算，不恢复旧结果冒充成功。

### 2.9 外部读取、状态栏与调度

| 来源 | 读取上下文 | 初始记录位置 | 调度归属 |
| --- | --- | --- | --- |
| 消息内函数 | 当前调用位置及其已生效 API 操作后的工作状态 | 调用点下方 | 当前处理批次；主流程等待期间仍可执行这些 API |
| 托管消息内状态栏 | 所在楼层对应的工作状态，保留 ready 规则 | 所在 AI 消息末尾 | 按现有楼层/Swipe 绑定安排执行 |
| 外置脚本/状态栏 | 当前有效工作状态或现有接口指定状态 | 现有 API 选定目标的末尾 | 外部请求顺序处理，独立批次可防抖保存 |

“最新”不取消位置含义，也不允许读取上一聊天状态。托管状态栏的楼层就绪和最终呈现不能因局部变量已应用而提前发生，不要求每块重建 iframe。

无关外部写入不能任意插入当前函数执行过程。落在未完成消息末尾的请求，等待消息推进至该位置再应用；不能先执行末尾写入，再执行它前面的消息块。等待的外部请求不能堵住当前函数自己的 API。只读请求无需统一阻塞。

message、branch、always 保持既有含义，scope 记录在工作状态中即时更新，保证保存前连续请求的去重也正确。不按函数名去重，不因某函数运行而全局禁用其他调用者的 history、sync、statusbar。消息内函数位置上下文禁止所有sync调用（默认、auto、latest、full及rollbackTo），明确返回错误，不入队、不延后。外部调用保持原有同步及回退功能。

### 2.10 批次保存与恢复生命周期

**确定范围的处理：** 在其有效工作状态上顺序处理整个范围，通常结束时保存一次。每条消息完成时先在内存清理临时进度；末条消息完成后统一保存累计消息变更及 Sidecar。函数内部 commit 归入当前批次，不启动独立防抖或强制刷盘。

**独立外部 API：** 第一条请求建立或接续有效工作状态，后续请求依次应用并立即返回应用回执。防抖窗口结束后批量保存，并设最长未保存时间，避免持续请求无限推迟保存。具体时间参数待接口实现确定。

**保存期间的新操作：** 本批保存使用确定的消息与状态版本；后到操作进入后续批次。完成本批保存只能清理该批已保存内容，不能覆盖新状态或清掉后来操作。保存与执行必须保持可解释的顺序，不增加另一份独立权威状态。

**保存顺序：** 先保存消息操作记录、done及必要恢复信息，再保存对应 Sidecar。变量、函数库、累计回退日志、scope 和“聊天处理到哪里”的依据作为一致的状态保存。不先持久化 done 再单独补其操作记录。保留目标版本检查和实际保存确认，允许无关消息新增，但不能刷新依据后覆盖被编辑的目标。

**中断恢复：**

| 重开时的事实 | ERA 行为 |
| --- | --- |
| 原消息已保存，计算结果尚未保存 | 根据实际消息重新计算 |
| API 记录及 done 已保存，Sidecar 尚未跟上 | 对照处理依据重算，跳过 done 函数，补算普通记录 |
| API 仅在内存，消息记录也未保存 | 无法恢复这部分请求，不凭空补造操作；作者可自行重发 |
| 存在中断进度 | 依据已保存消息、状态和日志恢复或撤销后重算；不将内存 cursor 当成持久依据 |
| 证据不足以确定状态 | 报告具体恢复问题，使用现有恢复入口，不猜测并覆盖正确数据 |

不依赖关闭事件一定能够完成保存。正常运行期间 ERA 应负责保存和恢复；强制关闭后，优先通过重算让 Sidecar 与实际聊天一致。整个处理的完成通知在最终保存成功后发出；尾链只负责呈现和通知，不重复提交消息或 Sidecar。

## 4. 验收要求

- **逐块语义**：有/无函数均顺序计算，超过64块可完成；@a、@f()、随机抽取和日志与历史重算一致。
- **批量持久化**：确定范围内多个块及多条消息不逐块调用聊天/Sidecar保存；内存生效和最终保存分别取证，消息完成后无临时进度。
- **即时读回**：100 → 函数 await commit 改70 → get读70 → 后块乘2得140；API返回时允许尚未落盘，函数await不触发额外保存。
- **提交顺序**：多次不await的commit依接收顺序执行，连续await均能读回；不await后的立即get不被错误保证为已执行。scope沿用同一执行窗口首次准入，多次commit允许连续应用；后续窗口依据目标消息/活动分支已有记录跳过。保存防抖窗口不改变原有准入规则。
- **防抖与并发保存**：窗口内合并、最长等待生效；保存中到达的新请求不丢失、不被旧状态覆盖，回执和保存批次对应真实事实。
- **标记与记录**：有done无记录仍跳过，无done有记录仍执行；移除done不删除旧记录。函数/状态栏同格式，本轮不重复应用，done与记录一起保存。
- **压缩与历史**：记录移动/合并不改变有效语义和scope；done保留，旧楼新增调用影响后续楼层；旧操作区不成为done依据。
- **失败恢复**：函数部分成功后抛错、未注册、无操作；应用失败真实拒绝，应用成功后保存失败另行报告并恢复；聊天保存成功而Sidecar失败可重算补齐。
- **用户交互**：处理中编辑/删除/切Swipe/切聊天/取消及迟到结果不串目标、不覆盖用户内容；无关消息新增不被一律拒绝。
- **强制关闭**：用已保存聊天识别并重算不一致；仅内存请求丢失不当作必须恢复的功能失败，不以scope保证任意外部副作用恰好一次。
- **三阶段**：规划、正文、结算及开关组合；下一阶段读取正确工作状态，规划取消不污染上一楼。
- **外部读取与状态栏**：当前上下文即时读取，旧楼绑定和ready保持；末尾写入不越过前面的块，不阻塞函数API或造成死锁。
- **纯计算**：查询、快照、预览、压缩校验不执行作者函数。

ERA-Test-Pack 应记录真实调用次数、API中间读取及回执时点、操作文本、done、最终变量和持久化结果，并采集保存次数。函数专项必须新增独立canonical单项及对应连续综合场景，覆盖注册参数、执行位置、API顺序、表达式、done历史、scope、失败、候选回退、三阶段、重新生成、压缩查询、外部交互、保存恢复、上下文失效和禁止接口。每条新增单项至少映射一条正式综合路径，catalog检查遗漏；故障用例也须映射恢复综合。既有MSG-FCALL终值/文本检查不能代表全部要求通过。预期值只放 Evaluator，不写入被测输入。

真实酒馆验收统一通过 ERA-Test-Pack，使用本轮实际构建的分发物和独立 Artifact；不得拼接旧运行作为一次完整验收。按实际依赖构建 Service/Macro AOT、相关包和 app。

所有测试（包括短测试）运行前读取并使用 long-running-task-monitor skill。少量定向测试可用10分钟心跳；全量综合或全量细则从启动至结束均至少1小时。当前调用内结束的短测试直接验收，不留空心跳。分别报告机器检查、单测、真机专项/回归和人工验收。
