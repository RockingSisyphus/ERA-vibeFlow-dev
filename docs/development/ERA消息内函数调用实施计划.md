## 1. 目标与已有能力

角色卡作者通过 SillyTavern 注册 JavaScript 工具函数，自行定义参数和函数逻辑，支持条件、循环、字符串、多变量操作和异步调用。同名注册覆盖及工具执行复用酒馆能力；ERA 解析消息内调用，并提供绑定执行位置的 API 上下文。酒馆原生工具调用维持原有使用方式。

正式消息执行以一个 ERA 操作块为工作单元，普通消息与含函数调用的消息使用同一套逐块处理机制。规划、正文、结算，以及旧消息编辑后的正式同步均属于支持范围。

| 部分 | 改动前基线 | 当前实现事实（第一轮审核） |
| --- | --- | --- |
| 指令执行 | 六类 Variable/Function Insert/Edit/Delete 按原文顺序整楼计算 | 已接入逐块循环，但仍预先整楼计算，末尾及尾链存在重复处理 |
| 数值函数 | statFunc、$expr 及自定义数值函数 | 继续保留；逐块路径的消息起点引用和随机序列需修正 |
| 公共 API | commit 经 Service FIFO 完成保存后返回 | 已增加全局位置绑定，但函数内提交只收集操作，未兑现即时读回 |

## 2. 已确定的执行语义

### 2.1 逐块执行与最终状态

1. 按原文顺序读取下一个 ERA 操作块，执行并提交该块的变量变化、对应日志和进度，再处理下一块。没有函数调用的消息也逐块提交。
2. 执行期间，在消息中保存临时进度标记，以支持中断后继续；完成整条消息时清除临时进度标记和续做点，保留原指令、API 操作记录及函数 done 标记。
3. 每块成功提交后的累计状态是后续执行的依据。消息最终状态来自这条累计执行链，不能用另一份预先整楼计算的结果覆盖。
4. 消息起点的变量、函数快照及随机抽取序列跨块保持原有含义；改变执行粒度不改变 @a、@f()、表达式和保护规则。
5. 变量状态、对应回退日志与执行进度必须保持一致。保存失败不能报告成功，也不能留下无法正确回退的已提交状态。
6. 前面成功的块不因后面的块失败而撤销。保留进度，恢复时区分“从已提交位置继续”和“撤销旧效果后重算”，避免重复应用或遗漏。
7. 可以按执行预算分批续做，但不能给普通消息引入固定64块等新的处理能力上限。

已有正式楼层按块保存到 Sidecar；规划阶段使用本轮草稿及阶段状态，见 §2.7。异步任务必须绑定聊天、消息版本和执行位置；旧任务不得写入新的聊天或 swipe。

### 2.2 函数交接与 API 队列

到达需要执行的函数调用时，前面的操作块已经完成提交。消息处理在此暂停，Service 当前任务让出执行权，Host 在任务之外调用作者函数。不得占住正在等待函数返回的 Service 任务，再让函数等待同一队列，从而形成死锁。

函数内 API 以显式绑定的调用上下文进入既有 Service 提交路径，由同一 CRUD/表达式引擎处理。完成该次实际操作后，await 才返回；函数再次读取能看到已经成功应用的结果。函数结束后恢复消息，后面的块以更新后的状态继续。

```text
消息块：HP = 100 → 提交
函数 A：读取 HP = 100
        await API 将 HP 改为70 → 实际应用并保存记录
        再读取 HP = 70
函数结束 → 保存 done → 恢复消息
消息块：HP = HP × 2 → 提交
整条消息完成：HP = 140 → 清除临时进度
```

函数对象只存在于 Host。Service/Host 边界传递可序列化事实；不能在 Host 再复制一套变量引擎，也不能用全局“当前正在运行某函数”来识别 API 来源。

函数 API 已成功处理的操作，在恢复消息时不得再次应用。恢复事件只结算调用并继续执行，不能再复制一份同样的变量记录。

### 2.3 操作记录格式与初始写入位置

函数内调用 ERA API 产生的操作，使用**与消息内状态栏调用 ERA API 完全相同的记录格式**，包括既有事务/scope 表达。当前普通 API 使用 era_tx 包装 Variable/Function 操作；复用同一构造和保存路径，不建立函数专用的 EraFCallTx 操作区协议。

区别只有写入目标：函数 API 将操作记录插入当前调用下方，位于原先后续操作之前；状态栏 API 仍写到目标消息末尾。同一函数多次提交时，新记录接在本次调用此前已写入的记录之后，保持提交顺序，不能反向插入。

```text
前面的 ERA 操作
函数 A（执行后带 done）
A 的第1次 API 产生的普通操作记录
A 的第2次 API 产生的普通操作记录
原先后面的 ERA 操作
```

记录保留作者提交的含义：$expr 保存表达式，固定值保存固定值。调用位置仅用于本次插入，不构成函数与这些操作之间永久的归属或压缩边界。锚点失效时不能静默改为消息末尾写入。

### 2.4 两类标记及函数执行判定

| 标记 | 用途 | 清除规则 |
| --- | --- | --- |
| 临时块进度标记 | 记录本轮消息已经应用到哪里，支持中断续做 | 整条消息执行完成后清除 |
| 函数 done 标记 | 表示这一处函数已经尝试执行 | 完成消息和压缩均保留；用户可手动移除以再次执行 |

**判断函数是否已经执行过，只依据该调用有没有 done 标记。** 不能根据下方是否存在操作、专用操作区、调用历史、函数名称、参数或另一个执行清单推断。

- 有 done：跳过函数本体。消息中的普通 ERA 操作按其当前位置及正常重放规则处理，不要求在该函数下方寻找操作。
- 无 done：正式同步运行到该处时尝试执行。即使有之前留下的操作，仍应执行。
- 每一处调用独立判断；同名同参的不同调用互不替代。
- 成功但没有变量操作的函数也写 done；失败处理见 §2.5。
- 修改带 done 的调用名称或参数，不会自动重跑。用户移除 done 后，下次正式处理再次尝试；已有操作不自动删除。
- 用户编辑旧楼新增无 done 调用，正式同步运行到那里时执行，并顺序影响后续操作和楼层。

当前已有自闭合调用语法，例如 `<EraFCall name="工具名" args='{}'/>`，实现用 `status="done"` 表达 done。准确的公开语法与上下文取得方式需要在接口文档中统一；无论采用何种写法，都不能增加第二种“已执行”判据。参数格式错误与嵌套引用识别属于解析规则，不是执行历史判据。

### 2.5 失败行为

函数抛出未捕获异常或 Promise 拒绝时，退出此次函数，报告错误，保留此前成功的 API 操作，保存 done，然后处理后续块。未注册函数同样报错并标记；已有 done 的调用不会自动重试。作者自行捕获异常继续运行的，ERA 正常等待其完成。

API 失败必须返回真实失败，不能把“已收集操作”报告为已应用或 committed。作者负责函数内部业务一致性及网络等外部副作用；ERA 负责正确的变量执行、记录和目标绑定。调用标记不承诺进程在外部动作与标记保存之间中断时，任意外部动作严格只发生一次。

消息中断时保留已成功块；规划会话取消遵守草稿边界。切聊、切 swipe、编辑或取消使原调用上下文失效时，迟到结果不得落到新版本；具体失效回执和草稿保留方式见 §5。

### 2.6 压缩与历史重放

函数留下的普通 API 操作正常参与既有压缩。**压缩可以移动、合并这些操作，不要求保持在原函数下方，不要求保留它们与函数之间的归属关系。** 需要保持的是普通变量操作的有效语义、scope 和重放一致性。

done 函数视为已处理的历史调用，压缩保留调用及 done，不执行它，也不因存在该调用而跳过整层压缩。后续函数重跑只能由用户移除 done 等显式消息编辑触发，不能由记录位置变化触发。

继续沿用封存楼层的压缩范围，最新 AI 消息不参与封存压缩。正式处理旧楼新增调用后再进行相应压缩；未完成楼层先恢复处理并清除临时进度。

普通历史查询、状态栏快照、预览、纯试算和压缩校验不执行作者函数。正式历史同步按 done 判定调用；已有普通操作按历史回退/重放规则重新计算，不把“本轮已应用一次”误解为“所有历史重算永久跳过”。

### 2.7 规划、正文与结算

```text
规划输出 → 顺序处理规划操作与调用，更新本轮草稿和阶段状态
→ 正文接收计划、函数结果与阶段状态
→ 正文完整接收并完成必要的原生收尾
→ 顺序处理正文操作与调用
→ 结算接收处理后的状态，顺序处理其补充操作与调用
→ 完成本轮最终消息及状态保存
```

规划没有正式 AI 楼层时，API 操作和标记写入本轮规划草稿；本轮成功后随最终消息保存。后续阶段读取规划处理后的状态。取消不能把这些操作追加到上一条 AI 消息。

规划 API 完成表示已经应用到本轮阶段状态，不能冒充已经保存到正式聊天楼层。正文开启独立结算时，其变量指令和调用仍然生效；结算提示词明确已经发生的变化，避免再次结算同一变化。

各阶段的可执行输出与报告引用必须结构化区分。消息调用不依赖 iframe 是否渲染或消息是否可见；这是一项目标执行规则，不表示曾经实现过渲染驱动调用。

### 2.8 外部读取、状态栏与并发写入

外置脚本的普通 get 可观察最新已提交块的状态。**块已提交与消息已完成是两个不同事实。** 托管状态栏的楼层就绪、最终呈现及生成阶段放行仍等待对应消息/阶段完成；不因每块提交而重渲染 iframe。

| 调用来源 | 读取状态 | 初始写入位置 | 调度要求 |
| --- | --- | --- | --- |
| 消息内函数 | 当前调用位置及其已成功 API 操作之后的状态 | 当前调用下方，按提交顺序 | 显式绑定上下文，Service 处理后返回 |
| 托管消息内状态栏 | 所在楼层的已就绪状态 | 所在 AI 消息末尾 | 保留楼层/Swipe 绑定和 ready 规则 |
| 外置脚本/状态栏 | 最新已提交状态或现有接口指定状态 | 现有 API 选定的目标消息末尾 | 保留普通队列和目标规则 |

如果外部写入的落点在当前未完成消息末尾，该写入等待消息推进到末尾再应用；不能先应用末尾操作，再处理它前面的块，造成实时与重放顺序相反。函数自身的 API 可以在交接期间被 Service 处理；队列实现不能让等待消息完成的外部请求阻塞这些函数请求。只读请求无需因末尾写入等待而统一阻塞。

scope 继续支持 message、branch、always 的既有含义，不按函数名去重。不能在函数运行期间全局禁用 history、sync、statusbar 或其他脚本的 scope。涉及重建同一执行上下文的接口需要明确回执与调度，见 §5。

### 2.9 消息收尾

只有确认消息已无待执行块，才进行消息完成收尾。临时进度的删除及续做点清除归提交路径处理；尾链负责最终呈现、通知等，不再次写同一份消息正文或 Sidecar 业务状态。

函数交接通知在交接点发出，不依赖“消息已完成”的尾链。更新来源核对不能简单替换为新依据而继续写旧文本；发生编辑/swipe 后，应正确重建或失效原任务。

## 3. 实施变更清单

| 范围 | 当前问题 | 目标修改 |
| --- | --- | --- |
| 正式同步 | 整楼预规划与逐块累计并存 | 逐块累计作为正式执行唯一状态来源；保持纯重放用于查询/校验 |
| 进度与日志 | 中途状态、日志、cursor 不完全一致 | 块提交后可正确续做，也可正确撤销后重算；完成后清临时进度 |
| 函数 API | 全局绑定、只收集操作 | 显式调用上下文，复用普通 Service API 处理，成功后即时读回 |
| 操作记录 | EraFCallTx 专用区及重复写入路径 | 与状态栏 API 同格式，由实际 API 提交写一次；恢复端只结算调用 |
| done 判断 | 可受操作区等额外条件影响 | 只检查该调用的 done |
| 来源验证 | 回送只认楼号，刷新依据可能覆盖新文本 | 绑定调用版本；失效时不向新版本写回 |
| Agent | 正文隔离、规划草稿缺失 | 三阶段有序操作和阶段状态传递 |
| 压缩 | 文档要求固定调用与记录位置 | 普通操作正常压缩，允许移位，保留 done，不执行工具 |
| 尾链与呈现 | 已逐块提交后仍可能回到旧提交链 | 消息完成后仅做收尾，不重复业务提交 |
| 兼容性 | 起点引用、随机序列、64块限制及 API 限制 | 保留既有含义和能力，补充分批续做与并发排序 |
| 维护收口 | 旧辅助实现、重复会话与过时描述 | 沿实际生产调用链合并/移除无用实现，更新 descriptor 与作者文档 |

复用酒馆注册表、CRUD/表达式、保护规则、MK、Sidecar、历史回退、普通 API 记录构造、消息保存确认、状态栏和 Pack/Harness 设施。不是为了新调用重新实现这些能力。

现有已保存 EraFCallTx 等中间格式如何读取或转换，需要依据真实存量决定；兼容读取不得把“存在旧操作区”继续当成 done。新写入统一使用普通 API 格式。

## 4. 验收要求

- **块语义**：有/无调用均逐块保存；超过64块可完成；中断续做与完整执行一致；完成后无临时进度，done仍在。
- **即时读回**：100 → 函数 API 改70 → 函数读取70 → 后块乘2得到140；多次提交和读取均正确。
- **标记唯一性**：有done无操作仍跳过；无done有旧操作仍执行；只移除done后再次执行且不自动删除旧记录。
- **记录格式**：函数与状态栏 API 使用同一格式；函数多次记录初始插入顺序正确，恢复端不重复生成。
- **压缩**：函数记录可移动/合并，操作有效语义不变；done保留，正式重放不再次执行函数；不以固定位置或专用区作为通过条件。
- **失败与恢复**：部分 API 成功后抛错、未注册、无操作函数；保存失败、中途刷新、取消、切聊、编辑和切swipe。
- **历史与表达式**：前楼新增调用影响后续楼层；@a、@f()、随机抽取、变量/函数回退日志与旧语义一致。
- **三阶段**：规划、正文、结算及开关组合；下一阶段真实收到正确状态；规划取消不污染上一楼。
- **外部 API**：读取最新已提交块；托管状态栏保持楼层就绪语义；外部末尾写入与函数 API 并发不串目标、不死锁、不改变重放顺序。
- **纯计算**：查询、快照、预览、压缩校验不触发工具副作用。

ERA-Test-Pack 应同时记录函数真实调用次数、API 中间读取、普通操作文本、done、最终状态和持久化结果。现有六条 MSG-FCALL 终值/文本检查不能代表上述全部通过。预期值只放 Evaluator，不写入被测输入。

真实酒馆验收统一通过 ERA-Test-Pack；本仓提供明确的预构建 bundle，不自建替代联调流程。源码变更后更新实际引用的 Service/Macro AOT及相关包，再构建 app。按当前项目配置和用户要求选择并发；新增独立 Artifact，不拼接旧运行作为一次完整验收。

所有测试（包括短测试）运行前读取并使用 long-running-task-monitor skill，遵守项目测试规则。分别报告机器结构检查、单测、真机专项/回归和人工验收；不得以旧 bundle 的通过证明新源码正确。

## 5. 尚需确定的接口细节

下列细节不改变上面已确定的语义：

1. 预注册工具回调如何取得显式绑定的 ERA 接口；调用标签、参数编码、done及临时进度的准确公开写法。
2. 同一函数多次提交的临时插入游标、调用版本身份、普通 API 事务构造如何共用；现有中间格式的兼容处理。
3. message/branch/always 在旧楼重算和规划草稿中的窗口映射；正式保存回执与规划阶段应用回执的字段。
4. 函数调用主动 sync 或其他会重建当前消息的接口如何结算；避免自等待或失效上下文继续写入，同时不限制无关外部调用者。
5. 三阶段输出如何承载有序指令/调用，与原规划 calls、结算 operations及报告引用协同。
6. 取消、保存失败、编辑和迟到异步结果的失效回执及草稿保留方式；外部末尾写入在队列中的挂起/唤醒如何表达。
