## 功能覆盖与示例

新功能必须先确定归属专题，再提供RPG场景、可复制操作、预期结果与必要边界。共用era_demo路径；示例依赖的字段须先初始化。初级不讲函数/meta，作者指南只负责指路。API的每个公开成员、引擎内建函数、保护合法值和UI设置应能在对应专题找到，不凭旧文档推定存在。

作者文本先说明目标和结果，再给操作。只在真正因果、递进或对照处过渡；跨章引用直达相应标题。内部节点、修复过程和运行编号留开发交接，不进入作者正文。低频参数用紧凑表格，不反复复制通用限制。

## 单一来源与资源

作者文案只维护docs/author，不再手工维护app/doc和附加文件中的同名副本。给AI时发送对应Markdown原文。运行时模板及初始化提示词仍以现有resource_planner、共享era-example-resources为来源；它们是生产资源，不因删除旧文档而删除或改变。

文档内HTML骨架用于说明环境；完整默认模板通过UI取得，不额外复制默认模板全量源码。需要发布文档附件时直接采用这些现行文件，不形成第二份手工修订源。

ARCHITECTURE、SVG、catalog及覆盖矩阵从现有命令生成，禁止手改生成结果。正式协议和类型保留真实来源，不新造影子接口。

## 更新和验证

1. 对照源码、类型与UI确认行为，再修改主要专题和相关短引用。
2. 检查示例的JSON、标签、表达式和函数参数；新增可执行例子使用现有测试工具定向验证，不为文字修订重跑全量。
3. 检查仓内链接、资源引用和生成资料来源；删除旧文档时同时移除其现行入口。
4. 按项目规则监控必要测试；结果写当前交接，完整日志和Artifact放运行资料目录。
5. 分仓提交文档与对应测试定义，明确是否修改产品行为。历史记录由Git保存，不重建永久任务报告目录。

## 节点与数据流说明规范

名称优先采用“具体对象＋动作”，说明面向不了解后台代码的读者。先说业务对象、实际动作和结果用途；保留会影响使用结果的保存时机、保护、失败和取消条件。源文件路径、内部函数名、框架对象、迁移历史和接口字段罗列放开发资料，不作为读懂节点的前提。内部引用编号保持稳定，显示名称可以独立改进。整体阅读入口见[工作流阅读指南](工作流阅读指南.md)。

读者可能完全不了解 ERA 内部，也没有读前后节点。每个 `desc` 应能独立说明当前节点处理什么、为什么放在这里、具体怎样处理及产生什么结果。适合中文的名称、说明和数据流注释使用通俗中文；技术 ID、API 名、schema 字段和代码符号保留准确拼写，在首次必要使用时解释含义。

- **Node descriptor**：说明可复用节点本身的真实职责、输入对象、判断依据、具体动作、重要分支和输出。明确是只准备数据、修改内存、保存消息/Sidecar，还是更新显示；涉及顺序、取消、失败、回滚或外部副作用时，说明相应边界。
- **Config 中节点调用的 desc**：说明这次调用在本流程中的对象、作用、关键分支与结果去向。不能只复制通用 descriptor，也不能要求读者先认识邻居节点才看得懂。
- **Nodeset 的 desc**：说明组合流程的目标、输入与输出、内部阶段和执行顺序、循环继续/结束条件及恢复边界。不能把其内部某一步的职责概括成整个 Nodeset 的工作。
- **数据流说明**：写数据的业务含义、来源、由谁处理、何时有效及如何使用；区分待执行请求、内存结果和已保存快照，不只重复资源名或类型名。

说明可按“处理对象 → 判断依据 → 实际动作及分支 → 结果与此处意义”组织，按真实复杂度写成几句完整话；简单入口或终态不强凑长文。不得只写“准备”“推进”“适配”“允许完整启动”等抽象词。MK、Swipe、Sidecar 等术语在理解当前节点所必需时用中文解释。

正文从实际功能说起，以具体对象和动作解释用途。写“记录消息开始前的变量，供历史回退恢复”，比“维护原语义边界”更容易理解；写“待提交正文由消息任务统一保存”，比罗列本节点不承担的职责更清楚。历史修复说明、层级辩护和对假想误用的反复否定留在开发记录中。影响实际结果的保存时机、保护拒绝、取消和恢复分支仍应说明其条件、原因与结果。

审校时把每个 Node、Nodeset 及调用单独拿出来读：读者应能说出它处理的具体资料、执行的动作、重要分支及输出用途。必要术语在这段说明中就地解释，例如把“候选”说成“一次模型生成结果”，把“帧”说成“作者函数运行进度”。调用说明还需给出这次处理的场景，数据连线用业务含义区分待执行请求、内存结果和已保存内容。可读性由结合源码的逐项阅读判断。

例如，启动位置判断不只写“character 允许完整启动”，应根据实际实现说明：“读取当前 ERA 脚本的启用位置，区分角色卡内部、全局脚本域和预设等环境；为每种环境给出该实例可执行的业务与呈现范围。多个实例同时存在或位置无法识别时，描述源码实际采用的策略及理由。”这只是写作示例：实际 desc 必须写出源码中具体策略，不能臆造主实例选举、停止其他实例等行为。

审校先阅读真实 Node source、调用 Config、descriptor 和合同，再写说明。函数调用不能说成已经保存，DFS 不能误写为另一种算法，适配/终态节点不能被赋予未实现的核心职责。抽象内部逻辑尚未在工作流中展开时如实说明，不用文案或虚假边伪装为已拆分执行结构。

正式 SVG 中应直接可读完整 desc，不仅存在于 tooltip/metadata，也不以截断短句替代完整说明。修改真实元数据后，通过 VibeFlow 命令更新 Architecture 和图，检查展开图的正文、节点名称、数据流、换行与遮挡，禁止手改生成结果。检查五个 root 的可达调用；不可达适配节点仍按真实源码维护说明，不为了出现在图中添加假调用。

仅元数据修订，核对执行字段未改变并运行适用的结构/文档检查，不因此重跑昂贵全量业务 suite；若改变了执行内容，则按[回归测试与问题处理](回归测试与问题处理.md)重新建立业务验收。文案审核通过不能代替功能验收。
