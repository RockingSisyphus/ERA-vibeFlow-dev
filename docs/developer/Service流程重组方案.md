## 要解决的问题

主循环同时展示任务资料准备、执行请求拆包、生成后的接续、结果转换和批次结算，读者需要跨越多条数据线才能拼出一次任务如何结束。核心消息图又把模板继承、字段入栈、日志追加和进度封装等动作拆成独立 Node，读者容易在实现步骤中丢失“这一段在完成什么”。

本方案按完整业务动作划分 Node，按输入和输出责任划分 Nodeset。图上的分支回答“接下来完成哪种工作”，细节算法放入相应动作的实现，源码中仍能追溯这些算法。

### 主循环：把准备、执行和返回结果各自放在明确的位置

新增 `era.task.prepare`，统一读取当前任务所需资料，准备初始化、脚本接口、模型生成、历史同步或简单任务的请求。简单任务的设置读写仍在执行入口完成。

主循环使用一个执行动作选择节点，同时取出选中分支的请求，减少“先选分支，再拆一次包”的中转。变量提交、历史同步和生成候选仍直接连接共享执行流程。生成候选完成后，单独选择它所需的历史同步、消息标识结算或直接结果，避免把生成前的准备与生成后的接续混在一起。

结果接收和接口回执转换合并为“形成原调用方需要的任务回执”。提交、同步和简单任务有不同结果类型；该节点按原请求来源处理实际到达的结果，再交给批次结算。

### 任务接口：保留两种对读者有意义的命令

`task_api` 保留提交变量操作（commit）和按历史重算（sync）两条分支。同步请求的参数检查、任务建立和输入失败结果归为一个动作。工作台草稿的变量、函数和有序编辑规划继续在原 Nodeset 中展开，这些分支对应真实的用户编辑方式。

接口提交流程把读取允许处理范围和请求分类归为“读取提交范围，识别操作或工作台草稿”；把建立事务、读取真实目标消息和准备共享执行状态归为“定位目标消息，准备本次提交”。跳过和失败回执归为即时结果，已应用的操作返回内存应用回执。实际保存仍由原任务的后续流程负责。

### 消息核心：提高到完整处理动作的抽象层次

消息块先识别当前要处理的内容，再选择正文指令、作者函数、生成阶段调用、跳过或消息结束。指令完成后统一接收变量、函数和日志；一条消息结束时统一整理历史、准备压缩并前进到下一条消息。

作者函数仍展示启动、等待、处理提交和结束。它提交的指令回到当前正文位置应用，应用完成后再回告函数。读取正文与作者等待的关键边界留在图上。

指令操作按新增变量、修改变量、删除变量、整组函数修改和生成阶段函数调用划分。变量操作包含自身的模板处理、公式计算、字段遍历与日志记录。函数组在候选副本上按原顺序完成全部修改和检查，整组通过后整体应用。

## 实施约束与验收

- 默认 Nodeset/Loop 展开层数继续不超过 4。任务准备是新分组；共享消息执行仍在主循环下一层，避免把核心执行再包进一层。
- 事件先后顺序、任务顺序、回执格式、Host 权限和保存时机沿用现有行为。内部请求类型增加简单任务分支，外部 API 格式保持原样。
- 变量对象字段按原顺序遍历；公式使用执行到该位置时的变量、历史起点和随机进度。函数组的整体应用和失败时原库保留也沿用现有规则。
- 作者请求的等待、提交应用、回告、取消和终结释放按原先的先后关系执行。合并后的实现需要保留原有停止检查与错误处理位置，不能因一个 Node 包含更多代码而吞掉中间错误。
- 历史回退、正文替换、消息标识、压缩和独立状态文件保存仍走共享机制。

实施时先建立新动作的 descriptor、中文说明、输入输出契约和实现，把现有算法归入对应动作；然后移除被替代的独立调用和包装。复用的业务算法保留。删除旧 descriptor 或源导出之前核对整个仓库的引用，避免影响其他入口和探针。

获批后按实际证据进行 Architecture、validate、quality、AOT/构建和执行探针检查；重点验证事件顺序、作者提交回告、函数组失败、随机序列、删除历史回退和接口保存回执。之后重新进行同一最终 bundle 的全量综合与全量细则。存量质量警告的清理继续按用户先前决定暂缓。
