# ERA 开发总览

ERA把消息中的变量操作变成可恢复的历史。角色卡作者通过标签、表达式和公共API操作数据，酒馆负责聊天与生成，酒馆助手负责脚本及消息iframe。作者用法见[作者指南](../author/README.md)，本章只解释维护边界。

## 模块关系

| 部分                                          | 职责                                                            |
| --------------------------------------------- | --------------------------------------------------------------- |
| `javascript_project/service`                  | 异步业务服务：历史定位、逐块执行、函数调用、候选恢复、API及保存 |
| `javascript_project/macro`                    | 同步宏解析和投影                                                |
| `javascript_project/expression`、`compaction` | 表达式求值与安全操作压缩，作为业务能力被调用                    |
| `app/src/ERA变量框架`                         | 唯一浏览器入口、Tavern适配、UI及生命周期装配                    |
| `packages`                                    | 跨层合同、快照、宏语法、工作台和共享示例资源                    |
| `generated`                                   | AOT构建输出，不手工编辑                                         |

维护时从所选root的vibeflow_project和ARCHITECTURE沿source定位真实代码。接口事实以源码、schema及`app/@types`为准；没有独立手写一套DTO文档。上游参考不是ERA生产实现。

## 一次购买的生命周期

AI输出购买调用前，普通块先依次修改本次内存状态。到调用位置，作者函数获得绑定参数的API，提交扣钱和增加食物；同一引擎应用这些操作，再继续后面的块。记录写在调用下方，done标记控制以后是否重执行。

运行中内存工作状态与已保存Sidecar分开；commit回执确认内存应用，完整任务或保存窗口结束后先保存消息，再保存Sidecar。普通呈现和ready等待对应保存边界。历史改变时撤销旧效果并重算，目标版本不符时不得覆盖用户新内容。函数位置请求不排到等待自身结束的外部FIFO，外部API和消息操作仍共用业务规则。

多阶段候选有恢复点，可纠错错误撤销整次候选，早前成功阶段保留。纯历史查询不执行作者工具。状态栏和单层模式只管理呈现与身份绑定，不另建变量权威状态。

## 构建与定位

使用仓库指定的Node、pnpm及Python环境；app当前采用Node24与pnpm10。安装依赖按锁文件及workspace约定执行，不改成本机另一套依赖。

```bash
python run.py verify-kernel
python run.py validate --config javascript_project/service/configs/era.service.jsonc
python run.py validate --config javascript_project/macro/configs/era.macro.jsonc
python run.py quality --path javascript_project/service
python run.py quality --path javascript_project/macro
pnpm --dir app verify
pnpm --dir app build
```

AOT构建采用所选root的VibeFlow命令；先读kernel命令规范，生成物由命令刷新。workflow、Config、Nodeset或执行结构变更遵守AGENTS的四类清单和架构审核；文档整理本身不构造虚假的执行结构审核。

联调优先使用现有酒馆页面及宿主公共接口。`pnpm --dir app dev`提供静态资源和监听；本机端口不能冒充接口事实。修改跨宿主/业务层时同时读局部AGENTS，不在UI或宏中复制业务调度。

## 测试职责

ERA-Test-Pack提供业务场景、fixture、独立oracle；ST-Test-Harness负责真实动作、隔离、采集和Artifact；ST-Response-Lab提供本地固定模型响应。真实ERA测试统一经Pack，提供本轮实际构建的bundle，不修改业务预期掩盖失败。

执行步骤、批量修复循环、分段续跑、独立验收和心跳要求统一见[回归测试与问题处理](回归测试与问题处理.md)。每次真实测试启动前使用 `long-running-task-monitor`；启动约 10 分钟观察，健康后约 60 分钟检查，临近结束按可靠 ETA 调整。安全活跃的 suite 不因个别业务失败停止测试或失去监控。

当前状态写入[交接说明](交接说明.md)，运行日志及 Artifact 存运行资料目录；任务记录按 skill 管理，任务结束停止监控，不永久增加历史计划/报告目录。未经用户明确授权不打开 human-review，不推送 Git 或进行发布。
