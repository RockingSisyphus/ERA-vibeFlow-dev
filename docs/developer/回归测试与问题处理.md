# 回归测试与问题处理

本章规定 ERA 重构、修复后的业务测试循环；AGENTS.md 和心跳提示词应沿用这些规则。测试数量以当轮实际选集为准：本轮冻结选集包含综合 `era-regression-integrated` 499 路、细则 `era-regression-all` 927 路，不把这些数量变成永久上限或门禁。专项和定向复跑不能代替全量。

## 准备与版本边界

1. 修改执行结构前，按协同协议在真实 Config 原位表达 planned 改动，维护复用、修改、删除、新增四类清单，生成完整正式展开审核图；得到后续明确批准后实施。路线选择不替代对真实审核图的批准。
2. 实施后更新 Architecture，运行适用的 validate、quality、Browser AOT、普通及沙箱测试、App verify、生产构建与 G3/G4 执行探针。核对本轮结构目标，既存警告单独报告，不通过隐藏或搬移警告声称改进。
3. 记录实际生产 bundle、源码检查点、测试包与原选集版本、执行命令、工作目录、日志和 Artifact 位置。版本记录用于关联结果，不给 Harness 另造摘要资格门禁。运行中不改 bundle、测试输入、动作、业务断言或 Host 安全检查。
4. 真实 suite 顺序运行，不同时启动两套。长作业优先使用独立于 Codex exec 会话的进程管理方式，例如用户 systemd 单元；保存真实退出状态与日志。会话消失只说明观测或进程异常，不能直接断言 Codex 超时或 ERA 功能回退。

## 综合、细则与批量修复循环

### 先综合，再细则

- 先跑全量综合。个别独立 Evaluator failed 时保留只读证据，标记整套未通过；只要作业仍活跃且继续运行没有具体破坏风险，就让全部路径自然跑完。不得因第一条失败停止、并行重启，或在运行中修改代码和预期。
- 收尾后审计全部结果，一次性整理失败路径、输入与动作、首次行为分歧、实际结果与预期、原因及证据。区分产品回退、测试定义问题、采集/环境故障和原因未明；必要时只跑对应的少量细则定位，不先扩大测试范围。
- 集中修复这一批问题，保持原业务期待；先定向复跑上一轮失败的综合路径。定向全部通过后，重跑全量综合；若仍有失败，重复整批归因、修复、定向复跑与全量综合。
- 全量综合通过后才跑全量细则。细则同样先收集完整一批问题，再集中修复；先复跑上一轮失败细则，全部通过后再跑全量细则，直到完整覆盖通过。
- Harness 安全中止可能使 suite 无法跑完；不绕过安全检查强行继续。先保存现场、检查是否还有活跃资源，确认安全恢复边界后补跑缺失或无效路径。业务失败本身不构成提前停止安全作业的理由。

### 两套结果必须属于同一最终版本

细则阶段若修改了 ERA bundle 或测试行为，上次综合通过不能自动沿用：全量细则通过后，额外跑全量综合。若该综合又需要修改代码，综合通过后再跑全量细则，如此循环，直到两套完整结果均对应同一最终 bundle 和测试定义。细则阶段没有这类改动时，不额外重复综合。纯说明修改若已确认不改变执行内容，不使原业务结果失效，也不记为新的业务验收。

细则发现综合未检出的产品回退，当前任务仍必须修复；同时记录到“综合覆盖缺口待办”：细则 ID、关联功能/综合路径（没有则注明）、原输入、关键动作、首次分歧、预期/实际结果、原因、修复及 Artifact 证据。主任务全部验收后再处理综合覆盖改进，不能在主任务中默默改变选集或声称已补足覆盖。

## 同轮前缀共享

森林版 Harness 以原 ID 和冻结的完整动作定义核对覆盖。正式命令按顺序选择 `--suite era-regression-integrated --suite era-regression-all`，细则依赖综合通过。两套重合的 420 个 ID 可指向同一 run 中的物理实录。选集、未执行项、叶子评估器状态和物理来源分别读取 `metadata/suite-results.json`。物理动作减少不会增加逻辑覆盖数；综合未通过时，细则阶段的阻塞和未执行项保留在报告中。按原 ID 单点仍可复现完整准备和后缀。

## 中断后的分段续跑

长跑意外终止不使已完整验证的路径自动作废，也不意味着整套通过。恢复按原选集逐路径进行，不虚构路径内部的中途恢复能力。

1. 先确认没有旧作业仍在运行或写同一输出目录。审计原 Artifact 后更新当前汇总及每条尚未解决失败的一份最新详细证据，按本章保留规则清理旧批次；不长期保留整套历史 Artifact。
2. 以原选集 ID 和原路径定义为基准，分别列出完整有效 passed、failed、partial、aborted、未录制及缺损路径。采集完整但 Evaluator 未通过的路径不能计入有效结果。
3. 用原输入、动作和 Evaluator 预期补跑没有有效 passed 的路径。新版使用 Harness 的 reconcile 命令核对候选、环境及原 ID，按 remainingIds 从原 V3 树选择叶子，保留其祖先和原 evaluator，依序写入新 Artifact。
4. 逐份核对跨 Artifact 的结果，为每个原 ID 选取恰好一份完整有效 passed，记录到当前汇总；成功详情、重复尝试和已经解决的失败详情随即删除。仍未解决失败只留一份最新详细证据，不计入有效覆盖。每个成功续跑段须先完成终态审计，不能把原中止 suite 改写为成功；其 aborted/incomplete 状态仅作为当前覆盖边界说明。
5. 对账原选集每个 ID、定义、必需 Evaluator 与动作，确认有效覆盖无缺失、无重复、无损坏；报告称“分段覆盖通过”，不能称“单份完整 suite 通过”。产品或测试行为改变后，不跨版本拼接有效全量成绩。
6. 临时选集在原定义、结果记录与必要证据保留后才清理，只清理本任务创建且归属明确的文件。

## 独立验收与归因

### 当前结果保留规则

按用户2026-11-12明确要求：只保留一份当前最新结果汇总，不保存历史批次或历史压缩包。汇总列明实际版本、范围、逐ID状态、缺失项与退出状态；不同版本或范围不可拼成全量通过。成功只保留汇总，不留动作、截图、Console、trace及沙箱等详情。每条尚未解决失败保留一份最新详细证据供分析，后续验证解决后立即删除；新的失败详情替换同一条的旧详情。

审计和必要的失败分析在清理前完成。正在运行的输入、输出和依赖暂不改动，作业结束后立即收尾。当前工具、固定测试定义、源码与必要的当前回滚检查点属于工作输入，不因文件位于 reports 下被误删；不以“输入”名义保留已经不用的旧产物。正式审核预览每个工作流只留当前快照，并以官方 preview --reindex 更新索引。

每套或每段终结都读取 CLI 退出码、suite-manifest、全部 required `evaluations/*/era-behavior-contract.json` 与 `era-ui-contract.json`（按路径实际要求）、每路 manifest、actions 和 Console。核对：

- 原选集 ID 与 selected/recorded 数量、逐路动作数量及序号/状态；文件缺失、损坏或重复。
- 每条路径必需独立 Evaluator 的唯一性、status/result/findings；采集完成、CLI 退出 0 或其他路径通过均不能代替本路径业务通过。
- recorder audit 的 lifecycle、structuralStatus、recorderEvidenceStatus、monitoringStatus 与 issues；独立核对 CLI 最终审计，不只依赖辅助汇总脚本。
- Console error/warn 的实际记录与类别。故障注入、取消、预设切换等预期错误需对应路径及证据说明；新增非预期错误必须调查，不隐藏 Console、不放宽断言直接判通过。

原因报告分开写可观察的直接故障、已证实根因和未验证推断。比如控制 API 失联或弹窗遮挡证明执行条件失败；原路径单独重跑成功可以支持恢复覆盖，却不能证明深层并发原因已经查明。测试定义若确需纠错，先证明其与既定业务合同的差异，记录变化及影响，重新确定两套有效版本；不能把产品回退改成新的预期。

## 监控、暂停与恢复

每次启动全量、专项、单项或失败复跑前，必须读取并使用 `long-running-task-monitor`；不因短测试豁免。短测试结束即审计，不留下无用心跳。已有匹配心跳复用；目标模式按 skill 使用有界等待，不给同一作业再创建心跳。无活跃作业时，编码和等待正式审核不使用周期心跳。

本项目明确覆盖 skill 默认的异常立即暂停调度：**安全活跃的 suite 即使已有 Evaluator failed，仍保持唯一心跳 ACTIVE，跟踪至自然结束。** 保存证据并标记整套未通过，不杀进程、不并行重启、不重复通知同一失败。已有失败不妨碍其余路径的健康进展采用约一小时检查。实际破坏风险须先处理安全边界；没有活跃作业仍需监控后，异常分析、编码或必需用户决策期间暂停心跳。

暂停后继续主动分析假阳性、直接原因、根因和可行修复对结果的影响，优先实施已授权的最小、可逆、结果中性恢复；不把“报告失败”当任务终点。复测前更新自足提示词，再恢复同一心跳。只有剩余可行路线实质改变目标、已确认机制或用户可见结果且现有要求不足以裁决时，按 `critical-fork` 解释因果、代价、未知和恢复条件，请用户判断。

### 检查与调度

每轮先读任务 `TODO.md`、`执行备忘录.md`、`最终报告.md`，只做一次检查和一次决策。检查真实进程/会话或 systemd 的 ActiveState/SubState/Result/ExecMainStatus、进程活动、日志新时间、Artifact/sandbox 增长、路径/动作进度、已产生 Evaluator 与新 Console 信息。连接不到 user bus 是检查工具问题，不能直接判测试失败。不要因 swap 本身行动。

新作业/异常恢复约 10 分钟观察；一轮有可核验健康进展后立即改为约 60 分钟稳定检查。无进展维持约 10 分钟，连续三次无进展按异常分析；不凭进程存在判健康。接近结束且 ETA 有实测依据时按预计剩余时间取整分钟安排，不机械等待一小时。

每轮读取 heartbeat wrapper 的准确自动化 ID、当前 status/RRULE，与目标间隔比较；不同则同轮调用 automation_update。只有工具成功后才记为已更新，备忘录记录旧值、新值、原因和结果。中文记录任务当前状态、当前进度/总进度、从固定任务起点计算的已执行时长、当前任务与总任务预计剩余时长；无法估算要说明缺少依据。

### 心跳提示词必填内容

提示词不能只写“按 skill 执行”，必须使下次接手者无需翻旧聊天也能继续：

- 任务记录路径、开始时间、目标和最终验收条件；固定 bundle、原选集版本、当前阶段及已有效通过范围。
- 当前唯一作业的命令、目录、进程/服务/会话、日志、Artifact、最新进度和必要只读证据；禁止并行真实 suite 和运行中改版本。
- 本章的活跃失败继续监控规则、完整终结审计、统一归因、集中修复、定向复跑、下一套全量测试及最终版本闭环。**明确当前测试结束后具体做什么**，不能只监控到结束就停。
- 启动 10 分钟、健康 60 分钟、停滞与可靠 ETA 例外；每轮准确 ID/status/RRULE 核对与同轮更新；中文进度、耗时和两类剩余时间。
- 无活跃作业后的暂停、主动恢复与用户关键分叉规则；证据保留、临时选集清理和最终报告。
- 健康进展保持安静；原始失败和阶段通过不发整项完成提醒。真正需要新用户行动或全部验收完成后，调用 `codex-task-alert` 判断资格，完整说明留在当前聊天，不复制固定提醒命令或硬编码某次自动化 ID。

## 最终完成条件

本轮结构目标和适用静态、构建、执行探针通过；同一最终版本的全量综合与全量细则，每个预期 ID 都有独立 passed，动作、Console 分类和 recorder audit 已核对。分段结果有严格对账。更新当前交接与最终报告，区分离线检查、独立沙箱、既存警告、环境未知以及尚未验收的真实日常酒馆。完成获准清理并暂停心跳后，才按 `codex-task-alert` 资格发送一次整项完成提醒。
